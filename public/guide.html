Model guide

Three ways to lay out the same 12 rows

This demo exists because "let's partition it" keeps getting applied to scaling problems. The lab holds one fixture in three arrangements and lets you trigger each failure mode on demand — the headline numbers come out of the model, not a slide.

A model, not a database. "Replication lag" is a queue and "network hops" are counters. It exists to make placement mechanics legible — the numbers are real outputs of the code.

Feature one

The counters

Machines

How many machines hold the data

Partitioned: 1 machine. Sharded: 3 machines. Replicated: 3 machines. Sharding is the only arrangement that adds hardware — three machines' worth of CPU, disk, and write throughput.

Proves
Partitioning is a management feature, not a scaling feature — every partition shares one CPU, one disk, one write ceiling.
Key detail
People conflate partitioning and sharding because both "split the data" — the machine counter exposes the difference instantly.
Rows stored

How many total rows get stored

Partitioned: 12 rows. Sharded: 12 rows. Replicated: 36 rows — a full copy of every row on every node, because duplication is its mechanism.

Proves
Replication survives; it does not split. Nothing is divided — redundancy is the whole point.
Key detail
Partitioning is the only arrangement that neither adds machines nor duplicates rows — which is exactly why it is the one people get wrong.

Feature two

Partitioning — pruning vs full scan

On the key

A query that carries the partition key prunes

region = 'eu' touches one partition of three — 4 rows scanned instead of 12. That is partition pruning: the engine skips the chunks the key rules out.

Proves
Partitioning buys real things: pruning and cheap maintenance — drop last year's partition in milliseconds instead of deleting 30 million rows.
Key detail
Pruning only works when the query carries the partition key — the predicate must name the column the table is split by.
Off the key

A keyless query scans everything — on one machine

amount > 60 carries no partition key, so all three partitions and all 12 rows get scanned. And either way it is still 1 machine's write throughput.

Proves
Partitioning does not scale anything — it made the table easier to manage and not a millisecond faster to serve.
Key detail
The anti-pattern from the article: partitioning by month, then running the lookup your app actually does — WHERE customer_id = ? — and scanning every partition.

Feature three

Sharding — lookups, joins, scatter-gather

Point lookup

Carry the shard key, touch one machine

Lookup row-004 runs the id through the same hash that placed it — one network hop, one shard answers, 4 rows on that shard. This is the beautiful case: sharding is the only arrangement that adds hardware.

Proves
Sharding is the scaling move: 12 rows over 3 machines means three machines' worth of CPU, disk, and write throughput.
Key detail
Works only while the query carries the shard key — hash(id) % N decides placement for writes and reads alike.
Cross-shard join

A join across shards pays a hop per row pair

row-001 ⋈ row-007 live on different shards, so the join costs a network hop per pair — a tax a join-heavy relational workload pays constantly.

Proves
Sharded systems push you toward denormalized data — pick the shard key around the join (tenant, account, user).
Key detail
Same-shard pairs are a local join with 0 hops — colocation is the difference between free and expensive.
Scatter-gather

No shard key means fan out to every shard

"Group all orders by region" asks all 3 shards, scans all 12 rows, and merges three partial results — latency becomes the slowest shard's latency.

Proves
The query without the shard key is the expensive one — exactly like pruning, the predicate decides the blast radius.
Key detail
Fan-out count equals shard count: every extra machine makes unkeyed queries broader, not faster.

Feature four

Rebalancing — the hidden cost of adding a shard

hash % N

Modulo placement remaps most of the table

Change N from 3 to 4 and naive hash % N moves 8 of 12 rows — 67% of the table across the network while writes continue.

Proves
Resharding is the difference between a routine operation and a weekend of babysitting a data migration.
Key detail
With modulo, changing N changes almost every key's answer — the placement function is the problem, not the data.
Rendezvous

Consistent-hash-style placement moves ~1/N

Rendezvous (highest-random-weight) hashing scores each key against every shard and takes the max. A new shard only attracts the keys that now prefer it: 2 of 12 rows move, 17%.

Proves
Same data, same machine count — the placement function decides whether adding a node is cheap or painful.
Key detail
This is what Dynamo-style systems use; if you cannot afford hash % N rebalancing, choose it up front.

Feature five

Replication — it survives, it doesn't split

Stale read

Read a replica before the stream catches up

Write row-005 → v2 and the primary commits instantly while the change ships to replicas asynchronously. Read replica-2 now and you get v1 — the old row.

Proves
Replication lag is the normal state, not an outage — "a few ms behind" is what asynchronous streaming means.
Key detail
This is the read-your-writes violation behind "I posted it and it vanished" bug reports.
Catch up

Lag is a timing window, not a permanent state

One replication tick applies the queued writes and every node agrees at v2. The stale dot turns fresh.

Proves
Read capacity and survival odds go up; storage cost goes up too — 36 rows stored for 12 rows of data.
Key detail
The defenses are unglamorous: route reads-that-must-be-fresh to the primary, or use synchronous replication and accept the write latency.

Limits

What this demo does not claim

  • This is a deterministic in-memory model, not a database — "replication lag" is a queue, "network hops" are counters, and the hash functions are FNV-1a.
  • The 12-row fixture is chosen so the story is legible: balanced partitions, balanced shards, a rebalance that separates modulo from rendezvous.
  • Production systems stack all three techniques — sharded by tenant for writes, partitioned by month for archival, replicated for failover. The lab shows them apart so the stacking makes sense.
  • The numbers (12/12/36 rows, 1/3 machines, 8 vs 2 moved) are real outputs of the model — but they describe this fixture, not your table.
  • Nothing leaves your browser except the counters endpoint — all interactions run client-side on the same code the tests run.
